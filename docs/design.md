# skillset 詳細設計書

## 2. CLI 仕様と終了コード

### 出力形式と表示規則
CLI の各コマンド形式、出力チャネル、終了コードは README の仕様に準拠する。

- **プロジェクト表示**: リンクの追加や削除といった変更操作を行う前に、対象リポジトリのルートを `project: <absolute root>` の形式で出力する。
- **一覧表示形式**: リンクの一覧は、`<label>\t<absolute destination>\t<absolute source>` のタブ区切り形式とし、宛先（destination）の昇順でソートして出力する。
- **ヘッダー表示**: 管理状態に応じて、先頭に `active_set: <name>` または `unmanaged` を表示する。
- **診断出力**: 警告やエラーなどの診断情報は、すべて標準エラー出力（stderr）に出力する。

### 終了コードの契約
状況に応じた終了コードは以下のとおり確定する。

- **0**: 正常終了（リンク変更の成功、差分が存在しない場合、差分の検出・表示のみが行われた場合、および試行実行（dry-run）の完了。差分が存在すること自体はエラーとせず終了コード 0 とする）。
- **1**: OS や I/O のエラー、ならびに状態ファイル（`.skillset/state.json`）またはジャーナルファイル（`.skillset/pending.json`）の破損が検出された場合。
- **2**: コマンドライン引数の不正、Git リポジトリ外やベアリポジトリでの実行、設定ファイルの構文・構造の不正、および apply 実行時に選択された set のソースが無効または存在しない場合（ソースが管理対象の宛先ツリー内に解決される場合を含む）。
- **3**: リンクの競合（conflict）、ロック競合（busy）、保留中ジャーナル（`.skillset/pending.json`）の存在、親ディレクトリがシンボリックリンクまたは非ディレクトリである場合、安全でない宛先が指定された場合。また、status 実行時に設定ファイルが有効であっても要求されたソースが見つからない場合は、状態を broken と表示して終了コード 3 で終了する。

## 3. 設定ファイルの検証と読み込み契約

### コマンドごとの読み込み条件
コマンドの種別や引数に応じて、設定ファイルの読み込みと検証の振る舞いを明確に分ける。

- **status コマンド**:
  - set 名が明示された場合: 指定された set の設定を読み込んで検証する。
  - set 名が指定されない場合: 状態ファイルに記録された `active_set` を確認し、設定ファイルが存在していれば読み込む。設定ファイル自体が存在しない場合、あるいは設定ファイルから記録済みの `active_set` が削除されている場合は、警告を出力した上で記録済みリンクの検査のみを行い、リンクの削除を示唆するような表示は行わない。
  - 既存の設定ファイルの構文が不正な場合: 終了コード 2 で終了する。
- **未管理状態（unmanaged）および remove コマンド**:
  - 未管理状態における status や remove では、設定ファイルの存在を要求しない。
  - remove コマンドはいかなる場合も設定ファイルを読み込まない。

### 設定構造と値の検証規則
設定構造の検証は、設定ファイル内に記述されたすべての set を対象に行う。ただし、ソースディレクトリの存在確認は、現在選択されている set に対してのみ実施する。これにより、無関係な set の不備によって現在の操作が妨げられないようにする。

値の検証規則は以下のとおりとする。

- set 名は空でない文字列でなければならない。
- skill 名は正規表現 `^[a-z0-9][a-z0-9-]*$` に厳密に合致しなければならない。スキーマバージョンは整数値の `1` のみを許可し、agents は `codex` および `claude` からなる重複のない空でないリストとする（skills は空の指定を許容する）。
- ディレクトリのベース名と skill 名の一致要件は課さない。設定内の配置キーをそのまま配置先の名前に使い、`SKILL.md` 内に記述された名前との整合性は利用者の手動運用に委ねる。
- スキーマバージョンに対する真偽値（bool）の指定、空の agents 定義、キーの重複、未定義の未知フィールドはすべて拒否する。

### パス解決と対象ファイルの要件
ソースパスは `~/` によるホームディレクトリ展開のみを許可し、絶対パスのシンボリックリンクは `Path.resolve(strict=False)` を用いて解決する。

指定されたソースディレクトリは、読み取りおよび探索が可能なディレクトリでなければならない。また、その直下に読み取り可能で空ではない通常ファイルとして `SKILL.md` が存在することを必須とする。

## 4. 永続化データモデル

### 状態ファイル（`.skillset/state.json`）
管理下にあるリンクと現在の構成は、リポジトリ内の `.skillset/state.json` に以下の JSON 形式で記録する。

```json
{
  "schema_version": 1,
  "active_set": "string | null",
  "links": {
    ".agents/skills/name": "/absolute/canonical/source",
    ".claude/skills/name": "/absolute/canonical/source"
  }
}
```

- `active_set` が `null` の場合、`links` は必ず空の辞書 `{}` でなければならない。
- 状態ファイルが存在しない場合は、`active_set: null` かつ `links: {}` の未管理状態と同等として扱う。
- 空の set（リンク定義が存在しない set）を適用した場合でも、`active_set` にはその set 名を記録する。
- remove コマンドを実行した際、以前に管理されていた状態であれば `active_set: null` かつ空の `links` を書き込む。すでに未管理となっている状態での remove は何も行わない（no-op）。
- キー、型、重複、既知フィールドの有無を厳密に検証し、未知フィールドは拒否する。相対宛先パスは、許可された接頭辞（`.agents/skills/` または `.claude/skills/`）と有効な skill 名の組み合わせのみに制限する。記録するソースパスは、`.` や `..` を含まない正規化された絶対パスとする。
- 記録されたリンクの所有権を確認する際は、`os.readlink` が返す未解決の生文字列との一致で判定し、所有権の確立のために記録されたソースパスを再解決してはならない。

### ジャーナルファイル（`.skillset/pending.json`）
変更処理の中断に備え、適用操作の直前に `.skillset/pending.json` へ以下の JSON 形式で操作内容を書き出す。

```json
{
  "schema_version": 1,
  "before": {
    "schema_version": 1,
    "active_set": "string | null",
    "links": {}
  },
  "after": {
    "schema_version": 1,
    "active_set": "string | null",
    "links": {}
  },
  "operations": [
    {
      "action": "add | update | remove",
      "destination": "repo-relative",
      "source": "/absolute/canonical/source",
      "previous_source": "/absolute/canonical/source | null"
    }
  ]
}
```

- 使用前に、構造およびすべてのパスフィールドを検証する。
- 保留中ジャーナルが存在する場合、すべての変更操作および試行実行（dry-run）を拒否し、終了コード 3 で終了する。
- status コマンドの実行時に保留中ジャーナルが存在する場合は、設定ファイルを読み込まずに保留中であることを報告し、現在のリンク状態と before/after の期待値を表示して終了コード 3 で終了する。
- 破損したジャーナルが存在する場合は、終了コード 1 で終了する。
- 不整合な状態での自動復旧は行わず、手動での確認と対応を求める。

## 5. 差分計算と所有権判定ルール

### 差分判定の対象集合
差分の計算は、状態ファイルに記録された所有リンク（owned）と、設定で要求されたリンク（desired）の和集合を対象として実施する。

### 所有状態ごとの判定規則
各宛先について、所有状態と現在のファイルシステム上の状態を比較し、以下のように判定する。

- **管理対象外の既存の宛先（nonowned existing destination）**: 既存のシンボリックリンクの参照先が要求と一致していても、管理外の配置とみなし常に競合（conflict）として扱う。
- **所有されている既存の宛先（owned present）**: 参照先のソースが記録と異なる場合、または通常ファイルやディレクトリなどの実オブジェクトが存在する場合は競合（conflict）とする。
- **所有されているが存在しない宛先（owned absent）**: 要求集合（desired）に含まれていれば追加（add）とし、含まれていなければ削除・忘却（remove / forget）とする。
- **所有されており一致する宛先（owned matching）**: 要求集合と同じソースであれば維持（keep）、異なるソースが要求されていれば更新（update）、要求集合になければ削除（remove）とする。
- **記録のみの status（recorded-only status）**: 宛先が存在しないか壊れている場合（absent / broken target）は broken と表示する。
- **要求されたソースの欠落**: 要求されたソースが存在しない場合、status では broken と表示し、apply では設定エラーとして終了コード 2 を返す。
- **所有権確認の優先**: 実装上可能な限り、ソースの存在確認に先立って宛先の所有権確認を実施する。
- **壊れた古い所有リンクの更新**: すでに参照先が壊れている古い所有リンクであっても、所有権が確認できる場合は、有効な新しいソースへの更新（update）や削除（remove）を行うことができる。

## 6. ディレクトリ構造の安全性と変更処理手順

### 親ディレクトリと管理ファイルの安全性要件
ファイルシステムの改ざんや意図しない書き込みを防ぐため、以下の安全要件を課す。

- `.skillset`、`.agents`、`.agents/skills`、`.claude`、`.claude/skills` の各親ディレクトリは、関連する操作においてシンボリックリンクや非ディレクトリであってはならない。
- `state.json`、`pending.json`、`lock` の各管理ファイルは、存在する場合に通常ファイルでなければならず、シンボリックリンクであってはならない。
- これらの要件に違反している場合は、いかなる変更書き込みよりも前に処理を拒否し、終了コード 3 で終了する。
- ソースディレクトリ側のシンボリックリンクは許容する。ただし、ソースが宛先そのものである場合、宛先ディレクトリ配下に存在する場合、または解決後の実体が管理対象の宛先ツリー内に侵入する場合は、自己参照を防ぐため終了コード 2 で拒否する。

### 変更処理の実行ライフサイクル
状態を変更する処理は、以下の手順に沿って厳密に実行する。

1. **事前確認（preflight）**: `.skillset/lock` を作成する前に事前検証を行う。現在の状態ファイルおよび実際のリンクが要求と完全に一致している場合は、ディスクへの書き込みを行わない。この何もしない処理（no-op）を繰り返しても、state ファイルのバイト列や更新日時（mtime）は変更せず維持する。
2. **排他ロックの取得**: 変更が必要な場合は、`.skillset/lock` に対して `flock(LOCK_EX | LOCK_NB)` を行い、非ブロッキング排他ロックを取得する。
3. **再読み込みと再計画**: ロックの保持下で状態ファイルを再読み込みし、最新の状態に基づいて計画を再作成する。
4. **ジャーナルの書き込み**: 宛先に対するいかなる変更よりも前に、ジャーナルファイル（`.skillset/pending.json`）をアトミックに書き込み、`fsync` を実行してディスクへ同期する。
5. **操作の適用**: 宛先パスの昇順でソートされた操作を順次実行する。各操作を実行する直前に、親ディレクトリの安全性と宛先の実態を再検査する。
6. **状態の更新**: 一時ファイルへの書き込みと `fsync` を行った後、`os.replace` によるアトミックな置換で状態ファイル（`.skillset/state.json`）を更新する。
7. **ジャーナルの削除**: 状態ファイルの更新が完了した後に、ジャーナルファイルを削除する。

ロックファイルの削除（unlink）は競合状態を引き起こすため、`.skillset/lock` は削除せずそのまま残す。また、ジャーナル書き込み後にエラーが発生した場合はロールバックを行わず、ジャーナルを残したまま終了する。

リンクが不要とする空の親ディレクトリは再作成しない。また、remove コマンドによって親ディレクトリ自体が削除されることはない。

## 7. 読み取り専用操作とグローバル警告

### 副作用の排除
status や dry-run などの読み取り専用操作は、ファイル、ディレクトリ、ロックファイルを一切作成しない。

### グローバル警告の検査範囲
プロジェクト外の設定との競合を検知するグローバル警告は、現在選択されているエージェントのルートのみを対象に検査する。

- **codex**: `~/.agents/skills`、`~/.codex/skills`、および環境変数 `$CODEX_HOME` が設定されている場合は `$CODEX_HOME/skills`。
- **claude**: `~/.claude/skills`。

検査時はルートの重複を排除する。同一名称の `SKILL.md` が検出された場合は警告を出力するが、コマンドの実行はブロックしない。また、スキャン対象が読み取り不可である場合も警告のみにとどめる。ソースコードの実行やファイル内容のログ出力は行わない。

## 8. 内部モジュール設計と実行方式

### モジュール構成と依存方向

本パッケージは、Git ワークツリー配下のシンボリックリンクを安全かつ決定論的に管理するため、関心事に応じて 5 つの主要モジュールと実行用エントリーポイントに分割されている。

- `models`: 共有データ構造の定義および基本的な値検証
- `config`: 設定ファイルの構文解析・スキーマ検証およびスキルソースの健全性確認
- `planner`: ファイルシステムを変更しないリンク状態検査と適用計画の算出
- `storage`: ファイルロック、ファイルシステム安全性の検証、保留ジャーナルおよび状態ファイルの永続化、リンクの変更適用
- `cli`: コマンドライン引数の解析、Git ワークツリー検出、ユーザー出力の整形、終了コードの制御
- `__init__`, `__main__`: パッケージメタデータ（バージョン `0.1.0`）の保持と、CLI 実行へのディスパッチ

依存関係は上位から下位への単方向であり、循環参照を排除している。

```
cli
 ├── storage
 │    ├── planner
 │    │    └── models
 │    ├── config
 │    │    └── models
 │    └── models
 ├── planner
 ├── config
 └── models
```

最下層の `models` は標準ライブラリのみに依存する。`config` と `planner` は `models` を参照するが、相互依存は行わない。`storage` は計画立案のために `planner`、ソース検証のために `config`、データ型のために `models` を参照する。最上位の `cli` はすべての下位モジュールを呼び出して全体の実行を制御する。


### 内部インターフェース設計
内部 API は非公開とし、実装担当者が凝集度の高い型付きデータクラスおよび純粋関数で構成する。

- コマンドのエントリポイントは `main(argv=None) -> int` とする。
- 変更を行う関数（mutations）は戻り値として `None` を返す。
- 計画を作成する関数（planners）は計画データを返す。
- 設定や状態を読み込む関数（loaders）は型付きデータを返す。

### ランチャーの起動方式
`bin/skillset` は Python の shebang を備え、自身のパス（`__file__`）の実体（`realpath`）を解決した上で、リポジトリのルートパスを `sys.path` に挿入してから内部モジュールを読み込む。

これにより、リポジトリ外のカレントディレクトリからの実行や、ランチャー自体がシンボリックリンクされている環境からでも安定して動作する。外部ライブラリ（pip）への依存は排除する。

## 9. 実装体制・責務分離と検証計画

### 担当分担と依存関係
作業の整合性を保つため、担当者の役割と変更範囲を以下のように分離する。

- **担当 A（実装）**: `skillset/**`、`bin/skillset`、`tests/test_config.py`、`tests/test_planner.py`、`tests/test_storage.py`、`tests/__init__.py` を担当する。状態管理、計画、ストレージの実装を一人の担当者が一貫して受け持つ。ステップ 1 のゲートを通過した後にステップ 2 のゲートへ進む。
- **担当 B（独立した契約検証）**: `tests/test_cli.py` のみを担当する。一時的に隔離された環境（`HOME`、`XDG_CONFIG_HOME`、`CODEX_HOME`、git リポジトリ）を用意し、確定した CLI および JSON の契約のみに依存して `python -m skillset` をブラックボックス検証する。担当 A の成果物が利用可能になった段階で実行する。
- **リード担当**: `docs/`、README、全体の結合、最終確認を担当する。担当者間でのファイル変更範囲の重複は生じさせない。

### 検証項目と順序
検証は以下の順序と項目に沿って実施する。

1. **単体テストの実行順序**: `config`、`planner`、`storage`、`discover` の順で単体テスト（unittest）を実施する。
2. **ランチャーの動作確認**: リポジトリ内および外部のカレントディレクトリから `bin/skillset --help` が正常に実行できることを確認する。
3. **環境隔離の検証**: git の worktree 機能を用いたファイル隔離環境で動作を確認する。
4. **実環境での確認**: 実環境（`~/skillset`）に対する確認は、読み取り専用の status コマンドのみとする。

### 主要な検証ケース一覧
テストでは以下のケースを網羅する。

- 競合発生時に既存の実ファイルが変更されず保護されること
- 同一の参照先を持つ未所有シンボリックリンクが競合として検出されること
- リンク先や設定の改ざんが検出されること
- 削除されたリンクが正しく認識されること
- 壊れたソースを持つリンクの削除処理が正常に行われること
- set の切り替えおよび空の set の適用が正しく動作すること
- 設定ファイルの構文および構造の不正が適切に検出されること
- ソースパスの正規化処理が正しく行われること
- 読み取り専用スナップショットの整合性が保たれること
- ジャーナル保留状態での異常終了と手動リカバリの手順が機能すること
- ロック競合時に安全に処理が拒否されること
- 状態ファイルの破損、ならびに宛先やソースのパスエスケープが遮断されること
- 差分がない操作（no-op）の実行時に状態ファイルの更新日時（mtime）が維持されること
