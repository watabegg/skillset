# skillset 利用ガイド

本書は `skillset` の利用ガイドです。`skillset` は、プロジェクトごとに必要なスキルを Git リポジトリや作業ツリーへシンボリックリンクとして配置・管理するツールです。

## 目的と概要

全社や個人で共通して使用するスキルはグローバル環境に維持しつつ、プロジェクトごとに必要なスキルを適切な Git リポジトリや作業ツリーへ配置したいという課題があります。

`skillset` は、指定されたスキルのセットを各リポジトリや作業ツリーの所定ディレクトリへシンボリックリンクとして配置・管理します。手動での個別適用のほか、登録した親ディレクトリ配下にある Git リポジトリを検出して自動的にリンクを一括同期する機能や、ファイルシステムのイベントを検知して常駐同期する機能を備えています。なお、プロジェクト配下にシンボリックリンクを配置したこと自体によって、グローバル環境にある同名のスキルが隠蔽されるわけではありません。

### 動作環境と制約
- **対応ランタイム**: Python 3.11 以上
- **必須ツール**: git
- **対応 OS**:
  - 手動操作コマンド（`status`, `apply`, `remove`, `roots`, `sync`）: Linux、macOS
  - 自動常駐監視およびサービス管理（`watch`, `service`）: Linux 専用（inotify および systemd ユーザーサービスを使用）。非対応システムで実行した場合は終了コード 2 と明確な診断メッセージを返し、定期ポーリングへのフォールバックは行いません。
- **依存関係**: Python 標準ライブラリのみを使用（外部パッケージや pip による追加インストールは不要）
- **通信**: 外部ネットワーク通信は行いません

## フォルダ自動同期クイックスタート

複数のリポジトリが存在する作業ディレクトリを登録し、自動同期を開始する手順です。最新の自動同期仕様については `docs/automatic.md`、手動操作のコア設計については `docs/design.md` を参照してください。

1. **設定ファイルへのセット定義**:
   設定ファイル（`${XDG_CONFIG_HOME:-~/.config}/skillset/config.json`）に対象となるスキルのセット（例: `client-a`）を事前に定義します。

2. **対象ディレクトリの登録**:
   リポジトリ群が配置されている親ディレクトリと、適用するセット名を関連付けて登録します。
   ```bash
   skillset roots add ~/projects --set client-a
   ```

3. **手動同期の実行（任意）**:
   常駐監視を開始する前や、エージェント起動前に明示的な一括同期を行いたい場合に実行します。
   ```bash
   skillset sync
   ```

4. **常駐監視の開始**:
   ファイルシステムの変更をイベント駆動で検知して自動同期します（Linux 専用）。
   - フォアグラウンドで実行する場合:
     ```bash
     skillset watch
     ```
   - systemd のユーザーサービスとして常駐化する場合:
     ```bash
     skillset service install
     ```

## 起動方法と設定ファイル

### 起動方法
チェックアウトした配置から直接実行するか、リポジトリ内からモジュールとして実行します。
- チェックアウト配置からの直接実行:
  ```bash
  /absolute/path/skillset/bin/skillset --help
  ```
- リポジトリ内からの実行:
  ```bash
  python3 -m skillset
  ```
ランチャーは `readlink` や `realpath` を用いて自身のチェックアウト先を自動検出するため、任意の作業ディレクトリから実行できます。pip によるインストールは不要です。

利便性を高める手順として、パスが通ったディレクトリ（例: `~/.local/bin/skillset`）へランチャーのシンボリックリンクを作成して利用できます。
```bash
ln -s /absolute/path/skillset/bin/skillset ~/.local/bin/skillset
```

### 設定ファイルの配置場所
- **デフォルトのパス**: `${XDG_CONFIG_HOME:-~/.config}/skillset/config.json`
- **明示的な指定**: コマンドライン引数 `--config FILE` を指定することで、任意の設定ファイルを読み込めます。

### 設定の構造と記述例
設定ファイルは JSON 形式で記述し、バージョン番号（`schema_version`）、セット定義（`sets`）、および自動同期の対象ディレクトリ（`roots`、省略可能）を含みます。

各エージェントとプロジェクト内の配置先ディレクトリの対応は以下のとおりです。
- `codex`: `.agents/skills`
- `claude`: `.claude/skills`

設定例:
```json
{
  "schema_version": 1,
  "sets": {
    "client-a": {
      "agents": ["codex", "claude"],
      "skills": {
        "client-a-artifacts": "~/client-a/agent-skills/skills/client-a-artifacts"
      }
    }
  },
  "roots": {
    "~/projects": "client-a",
    "~/projects/external": null
  }
}
```

### 設定の検証規則
- **スキーマバージョン**: `schema_version` には `1` を指定します。
- **セット定義（sets）**:
  - セット名には空ではない文字列を指定します。
  - スキル名のキーには英小文字、数字、ハイフンで構成される正規表現 `^[a-z0-9][a-z0-9-]*$` に一致する文字列を使用します。
  - 定義したスキル名が配布元にある `SKILL.md` 内の `name` と一致しているかどうかは、利用者が自身で確認する必要があります。
  - スキルの配布元（`source`）は、絶対パスまたはチルダ（`~/`）で指定します。環境変数の展開は行われません。
  - `source` に指定するパスは読み取り可能なディレクトリであり、その直下に読み取り可能かつ空ではない通常の `SKILL.md` ファイルが存在していなければなりません。
  - スキル定義が空のセット（空の `skills`）は許容されます。
- **ルート定義（roots）**:
  - キーには絶対パスまたはチルダ（`~/`）で始まるパスを指定します。内部でチルダ展開およびパス解決（`resolve(strict=False)`）が行われ、正規化後の重複は拒否されます。
  - 値には設定ファイル内に実在するセット名の文字列、または自動同期を除外するための `null` を指定します。複数のセットを合成（composition）する機能はありません。
  - ルートのパス解決では最長一致祖先解決ルール（longest resolved component ancestor）が適用されます。単純な文字列の前方一致ではなく、解決されたパスの構成要素単位で最も深く一致する祖先のルート設定が適用されます。
  - 設定ファイル内のキーとして実在しないディレクトリが記載されている状態は許容されます（`watch` が再出現を検知します）。ただし、CLI の `roots add` や `roots disable` で登録する際は、解決後に実在する通常のディレクトリである必要があります。
  - ファイルシステムのルート（`/`）を登録することは、過度に広範で破壊的な探索を防ぐため禁止されており、指定された場合はエラー（終了コード 2）となります。ホームディレクトリ自体（`~`）は明示的に設定された場合のみ許容されます。
  - シンボリックリンクのディレクトリを登録した場合は登録時に一度だけ解決され、探索時にディレクトリのシンボリックリンクを辿ることはありません。
- **共通規則**:
  - 未知のフィールド、未定義のエージェント、重複したキーが含まれる設定はエラー（終了コード 2）として拒否されます。
  - 常駐監視（watch）が設定ファイルを自動で書き換えることはありません。

## フォルダ管理と自動同期（roots / sync）

### 対象ディレクトリの管理（roots コマンド）
自動同期の対象となる親ディレクトリの登録、除外、削除、一覧表示を行います。すべてのサブコマンドにおいて実在する設定ファイルが必要です（設定ファイルが存在しない場合は終了コード 2）。また、`roots add` を実行する前に、適用対象のセットが設定ファイル内に定義されていなければなりません。

- **ディレクトリの登録**:
  指定したディレクトリとセット名を関連付けて登録します。
  ```bash
  skillset roots add DIR --set NAME [--config FILE]
  ```
  設定ファイルの存在と指定されたセットの定義を検証した上で、正規化されたパスを `roots[DIR] = NAME` として登録します。設定ファイルの更新は、ファイル隣接のロック（`flock` ノンブロッキング、ビジー時は終了コード 3）を取得してファイルを再読み込みし、セットや他のサポートデータを保持したままアトミックに書き込みます。内容に変更がない場合はファイルの更新日時を変更しません。このコマンド自体はリポジトリの同期を行いません。成功時は標準出力に `registered\t<path>\t<set>` を出力し、終了コード 0 で終了します。

- **特定サブツリーの除外（オプトアウト）**:
  登録済みディレクトリ配下の特定のサブツリーを自動管理の対象外として設定します（`roots[DIR] = null`）。
  ```bash
  skillset roots disable DIR [--config FILE]
  ```
  最長一致祖先解決ルールにより、上位ディレクトリにセットが割り当てられていても、このサブツリー配下のリポジトリは自動適用の対象外となります。成功時は標準出力に `disabled\t<path>` を出力し、終了コード 0 で終了します。既存のシンボリックリンクの削除は行いません。

- **登録の解除**:
  指定したパスに一致する登録キーを削除します。
  ```bash
  skillset roots remove DIR [--config FILE]
  ```
  操作は冪等であり、キーが存在しなくても終了コード 0 で終了します。また、指定されたパスがファイルシステム上に実在しなくても削除可能です。登録が解除されたディレクトリ配下のリンク削除は行われません。上位の親ディレクトリにマッピングが存在する場合は、最長一致祖先ルールに従って親の設定が適用されるようになります。

- **登録一覧の表示**:
  登録されているパスとセット名（または `disabled`）をソートして標準出力に `<path>\t<set or disabled>` の形式で表示します（読み取り専用）。
  ```bash
  skillset roots list [--config FILE]
  ```

- **コマンド制約**:
  `add` および `disable` において、解決後のパスが通常のディレクトリでない場合はエラー（終了コード 2）となります。設定ファイルの形式が不正な場合も終了コード 2 となります。

### プロジェクトの検出と同期（sync コマンド）
登録されたルート配下の Git ワークツリーを検出し、マッピングされたセットのシンボリックリンクを一括適用します。エージェント起動前の明示的な同期手段としても使用でき、ラッパーの差し込み等は行いません。

```bash
skillset sync [--project-root DIR] [--dry-run] [--config FILE]
```

- **プロジェクトの検出仕様**:
  - 有効な各ルート配下を走査し、正規化された一意の Git ワークツリールートを検出します。
  - ディレクトリのシンボリックリンクは辿りません。
  - 有効な Git プロジェクトの末端（通常ファイルまたはディレクトリとしての `.git` が存在し、`git rev-parse --show-toplevel` の解決結果と一致する非ベアリポジトリ）に到達した時点で、その配下の走査を停止します。親リポジトリ内にネストされたリポジトリを管理する場合は、そのディレクトリを明示的に別個のルートとして `roots` へ登録する必要があります。親リポジトリ内に明示的に登録された子孫ルートがある場合は、親の末端到達後もその子孫を走査します。
  - 不完全または欠落した Git マーカーはスキップし、ファイルシステムのエラーは適切に報告します。
  - 除外設定されたサブツリー（`null`）は走査されませんが、その配下に明示的に登録された有効なルートがある場合は走査対象となります。
  - 走査時は以下のディレクトリを除外します（ドットで始まるディレクトリを一律に除外するわけではありません）。
    - 除外ディレクトリ一覧: `.git`, `.skillset`, `.agents`, `.claude`, `node_modules`, `.venv`, `venv`, `__pycache__`, `.cache`, `.tox`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `.next`, `dist`, `build`, `target`, `vendor`
- **同期処理の挙動**:
  - 実行ごとに最新の設定ファイルを読み込みます。走査前に設定ファイルの読み込みに失敗した場合、走査および書き込みは行わず終了コード 2 を返します。
  - `--project-root DIR` を指定した場合、その Git ルートを解決し、対応するマッピングが存在する場合のみ同期を実行します。マッピングが存在しない場合は `unmatched\t<path>` を出力して終了コード 0 で終了し、書き込みは行いません。
  - `--project-root` の指定がない場合は、検出されたすべてのプロジェクトをソート順に同期します。
  - リポジトリに既存の `active_set` が記録されており、それが今回選択されたセットと異なる場合は、過去に自動同期されたものであっても暗黙的な切り替えは行わず、衝突（終了コード 3）として停止します。
  - 既に手動で同一セットが適用されている状態のリポジトリは、自動同期の対象として継続管理できます。
  - 個別のプロジェクトでエラーが発生しても、他のプロジェクトの処理は継続します。
  - `--dry-run` を指定した場合、ファイル、ディレクトリ、ロックファイル、Git 除外設定の変更を一切行いません。
  - 出力制御: CLI の `skillset sync` ではデフォルトで結果の詳細が出力されます（`quiet=False`）。内部常駐監視から呼び出される際は、変更なし（keep）や対象外（unmatched）の出力を抑制し、変更やエラーのみを記録するモード（`quiet=True`）が使用されます。
  - 終了コードの集約規則:
    - 処理中に 1 つでも入出力エラーや状態ファイルの破損が発生した場合は `1`
    - 衝突、ビジー状態、または保留中の操作の残存が発生した場合は `3`
    - 配布元が無効な場合は `2`
    - すべて正常に完了した場合は `0`

## 常駐監視とサービス化（watch / service）

### イベント駆動の常駐監視（watch コマンド）
inotify を使用してファイルシステムの変更を監視し、リポジトリの作成や設定ファイルの変更に応じて自動的に同期を行います。Linux 専用のコマンドであり、フォアグラウンドで実行します。

```bash
skillset watch [--config FILE]
```

- **イベント監視の仕様**:
  - `ctypes`/`libc` を通じたネイティブ Linux inotify を使用します。非ブロッキングかつ `cloexec` なファイルディスクリプタを用い、待機時はセレクタによってブロックされます。定期的なファイルシステム走査や更新日時のポーリングは一切行いません。
  - タイマー処理は、変更通知のデバウンス（約 0.2 秒）、Git ワークツリー生成途中の上限付き再試行（0.2 秒、0.5 秒、1 秒、2 秒、5 秒）、およびシグナル処理にのみ使用されます。
  - SIGINT または SIGTERM を受信した場合はクリーンに終了します（終了コード 0）。
  - 単一デーモン排他制御: 設定ファイルごとに単一のデーモンのみ実行を許可します。`~/.local/state/skillset`（`XDG_STATE_HOME` が設定されている場合はその配下）の `watch-<hash>.lock` ファイルに対して `flock` をノンブロッキングで取得します（ビジー時は終了コード 3）。稼働中のロックファイルは削除しません。
- **起動時および監視の挙動**:
  - 設定ファイルを読み込み、走査を開始する前に設定ファイルの親ディレクトリ（または実在する直近の祖先）の監視を設定します。
  - ディレクトリ探索の境界を再帰的に監視し、既存のリポジトリを検出してそれぞれ一度同期を実行します。
  - 各リポジトリのルートおよび直下の `.git` ディレクトリのメタデータを非再帰的に監視します（ソースツリー全体は監視しません）。また、ネストされた登録スコープに至る祖先ディレクトリも監視します。
  - 子ディレクトリを走査する前にディレクトリを監視対象として登録することで、新規サブツリー作成時の競合（レースコンディション）を防ぎます。
  - 新規または移動してきたサブツリーを監視対象としてから、その既存内容を走査します。
  - `IGNORED_DIRS` を走査対象外とします（`.git` ディレクトリのメタデータ監視は専用に処理されます）。ディレクトリのシンボリックリンクは辿らず、`.agents` 配下のキャッシュリポジトリを走査しません。
  - 起動処理が完了すると、標準出力に `watch: ready` を出力してフラッシュします。待機中は何も出力しません。
- **設定ファイルの更新検知**:
  - 設定ディレクトリの書き込みクローズ、アトミックな移動置換、削除を監視します。
  - 有効な設定変更を検知すると監視対象を再構築し、一度だけ完全な再調停を実行します。
  - 不正な設定ファイルが置かれた場合は同期処理を一時停止し、エラーをログに出力した上で、修復されるまで監視を継続します（前回の正常な設定を適用し続けることはしません）。設定からマッピングが削除されても既存リンクの削除は行いません。不正な設定ファイルが原因でサービスが終了することはありません。
  - 登録されたディレクトリが存在しない場合は、実在する直近の祖先を監視して作成や移動を待ちます（自動でディレクトリを作成することはありません）。
- **イベント処理の詳細**:
  - 新規 `.git` マーカーやメタデータの変更を検知すると候補として登録し、デバウンス後に同期を試行します。ワークツリーの生成途中などで不完全な場合は上限回数まで再試行します。試行上限を超えても不完全な場合は保留としてログに記録し、将来のイベントを待ちます（定期的な再走査ループは行いません）。`git clone` などの処理中も、その後のメタデータ更新イベントによってトリガーされます。
  - 既存の有効なリポジトリ内における通常のソースファイルの書き込みは無視されます。
  - 通常のイベントでは、影響を受けるプロジェクトのみを同期します。
  - ディレクトリの名前変更や削除に応じて監視設定を更新します。処理直前にスコープ所属を再確認し、登録範囲外へ移動されたパスへの書き込みは行いません。
  - `IN_Q_OVERFLOW` やアンマウント、監視無効化が発生した場合は監視を再構築して一度完全な再調停を行い、警告をログに出力します。監視数上限などの永続的エラーが発生した場合は終了コード 1 と対処方法を返します。ルートディレクトリが削除された場合も監視を終了せず、祖先ディレクトリを通じて再作成を待機します。
  - 自身が管理する `.skillset`、`.agents`、`.claude` への書き込みは無視し、自己ループを防ぎます。
  - 実際の同期変更やエラーが発生した場合にのみログを出力します。

### systemd ユーザーサービスによる常駐化（service コマンド）
`watch` コマンドによる常駐監視を、Linux の systemd ユーザーサービスとして登録・管理します。Linux 専用のコマンドです。

```bash
skillset service {install,start,stop,status,uninstall} [--config FILE]
```

- **サブコマンドの動作**:
  - `install`:
    - `${XDG_CONFIG_HOME:-~/.config}/systemd/user/skillset-watch.service` を作成します。
    - 実行コマンドには Python インタープリタ、ランチャー、設定ファイルの絶対パスを適切にクォートおよびパーセントエスケープして記述します。
    - 既に自身が管理していない同名ユニットファイルが存在する場合は、上書きを拒否して終了コード 3 で終了します。
    - 作成後、`systemctl --user daemon-reload` および `systemctl --user enable --now` を実行してサービスを開始します。
  - `start`: `systemctl --user start skillset-watch.service` を実行します。
  - `stop`: `systemctl --user stop skillset-watch.service` を実行します。
  - `status`: `systemctl --user status skillset-watch.service` を実行し、その結果を出力します。終了コードは systemctl の結果（非アクティブ時は 3）を引き継ぎます。
  - `uninstall`: `systemctl --user disable --now skillset-watch.service` を実行し、作成したユニットファイルを削除して `daemon-reload` を実行します。
- **制約事項**:
  - `sudo` やシステム全体の systemd ユニットは絶対に使用しません。
  - 非 Linux 環境で実行された場合は終了コード 2 を返します。
  - ユーザー用 systemd が存在しない、またはアクセス不能な環境では終了コード 1 と明確な診断メッセージを返します。

## 手動操作と状態管理（status / apply / remove）

### 手動コマンド体系
個別リポジトリの管理には以下の手動コマンドを使用します。
```bash
skillset status [--set NAME] [--project-root DIR] [--config FILE]
skillset apply NAME [--dry-run] [--project-root DIR] [--config FILE]
skillset remove [--dry-run] [--project-root DIR] [--config FILE]
```

### プロジェクトルートの解決
- `--project-root DIR` を指定した場合、そのディレクトリをもとに `git rev-parse` を実行してチェックアウトのトップレベルディレクトリに解決します。
- Git 管理外のディレクトリやベアリポジトリに対して実行した場合は拒否されます。
- 作業ツリー環境に対応しています。

### 基本的な操作の流れ
1. 適用予定のセットの状態を確認:
   ```bash
   skillset status --set client-a
   ```
2. 変更内容を事前に試行（ドライラン）:
   ```bash
   skillset apply client-a --dry-run
   ```
3. セットを実際に適用:
   ```bash
   skillset apply client-a
   ```
4. 適用後の状態を確認:
   ```bash
   skillset status
   ```
5. 解除内容を事前に試行:
   ```bash
   skillset remove --dry-run
   ```
6. セットのシンボリックリンクを解除:
   ```bash
   skillset remove
   ```

### 状態管理の仕様
- 1つのチェックアウトに対して適用できるセットは1つに限られます。
- 別のセットへ切り替える際は、以前の操作で自身が作成した所有リンク（owned）のみが置き換えられます。
- 適用状態はリポジトリ内の `.skillset/state.json` に記録されます。
- `remove` コマンドは、設定ファイルやスキルの配布元が存在しない状態であっても、記録された状態情報をもとに解除を実行できます。
- `--set` を指定せずに `status` を実行した場合、アクティブなセットの設定が定義されていれば差分を表示します。設定ファイルやアクティブなセットの定義が存在しない場合は、警告を表示した上で記録されている状態のみを確認します。
- 未管理状態（unmanaged）の確認には設定ファイルは不要です。

### 実行時の挙動、出力、終了コード
- `status` コマンドおよび `--dry-run` オプションの実行時は、ファイル、ディレクトリ、ロックファイルの作成を一切行いません。
- 表示結果の行は配置先パス（destination）順に並び替えられ、状態（add, keep, update, remove, conflict, broken）が表示されます。
- 標準出力には実行計画や実行結果を出力し、標準エラー出力には警告やエラーを出力します。
- 終了コード:
  - `0`: 正常終了、または差分の検出
  - `1`: 入出力エラー、状態ファイルの破損、systemd ユーザーサービスへのアクセス不能、inotify 監視数上限エラー
  - `2`: 設定ファイルの不備、引数エラー、非 Git ディレクトリ、無効な選択元、非対応 OS（Linux 以外の watch/service）、非ディレクトリの roots 登録/除外、ファイルシステムルート（`/`）の登録
  - `3`: 衝突、ビジー状態（ロック取得失敗）、保留中の操作の残存、既存の他者製サービスユニットの存在

## 所有権管理と障害復旧

### 所有権の判定と保護規則
- 既存の通常ファイル、ディレクトリ、および自身が管理していないシンボリックリンクは、たとえ同じリンク先を指していても上書きしません。
- リンクの所有権（owned）は、シンボリックリンクのリンク先をそのまま読み取った値（raw readlink）が、状態ファイルに記録されている配布元（stored source）と一致するかどうかで判定します。
- 管理対象のリンクが手動で別のファイルやリンクに置き換えられていた場合は衝突として扱います。
- 手動で削除されていた場合は、`apply` の再実行時に再作成され、`remove` 実行時は対象外として無視（忘却）されます。
- 配布元の実体が壊れているリンク（broken source）であっても、`remove` によるシンボリックリンク自体の削除は可能です。

### 排他制御
- 操作時は `.skillset/lock` ファイルに対して `flock` を使用し、ノンブロッキングで排他制御を行います。
- ロックファイル自体は処理完了後も削除せず、そのまま残します。

### 保留状態の記録と中断時の挙動
- 変更処理を行う前に、変更前（before）、変更後（after）、および実行する操作内容（operations）を `.skillset/pending.json` に先行して保存します。
- 処理が途中で強制終了やクラッシュにより中断された場合、自動的なロールバックや自動再開は行われません。
- 中断後は `status` 実行時に保留中の操作が存在することが報告され、変更を伴う操作は終了コード 3 で拒否されます。

### 手動復旧手順
処理の中断が発生した場合は、以下の手順に従って手動で状態を復旧します。
1. 他の `skillset` プロセスが停止していることを確認します。
2. `.skillset/pending.json`、`.skillset/state.json`、および現在のシンボリックリンク群のバックアップを作成します。
3. `pending.json` に記録されたジャーナルの before および after の内容と、実際のシンボリックリンクの状態を比較します。
4. `before.links` の各リンク先と完全に一致する元のリンクを手動で復元します。
5. before に存在せず今回の操作で新たに追加されたリンクについては、after のリンク先と一致していることを確認した上で、リンク自体のみを削除します（配布元の原本ファイルは絶対に削除しません）。
6. 第三者による手動変更が確認された箇所は、自動処理を行わず目視で状態を確認します。
7. `state.json` をジャーナルの before オブジェクトの内容に復元します（未管理状態を表す場合も null や空にはせず、`{"schema_version": 1, "active_set": null, "links": {}}` の正確な状態オブジェクトとして保存します）。
8. 復元が完了したら、最後に `pending.json` を手動で削除します。
9. `skillset status` を実行し、状態が正常に戻ったことを確認します。

- ジャーナルファイルが破損している場合は、推測で修復せず、バックアップ内容をもとに状態を確認してください。
- 誤削除を防ぐため、汎用的な `rm -rf` コマンドによる一括削除手順は掲載しません。

### セキュリティ境界
- 配置先の親ディレクトリ（`.skillset`、`.agents`、`.agents/skills`、`.claude`、`.claude/skills` など）がシンボリックリンクである場合は処理を拒否します（スキルの配布元自体がシンボリックリンクであることは許容されます）。
- ただし、本ツールは悪意のある競合や不正アクセスを防ぐセキュリティ境界として設計されているわけではありません。

## Git 除外設定とグローバル環境からの移行

### Git 除外設定の管理
本ツールは共有リポジトリの `.gitignore` を自動編集しません。共有リポジトリの履歴を変更しないため、リポジトリローカルな除外設定（`info/exclude`）を使用します。

- **手動 apply 実行時**:
  手動で `skillset apply` を実行した場合、利用者が除外設定ファイルを手動で更新する必要があります。
  1. 以下のコマンドで除外設定ファイルのパスを取得します。
     ```bash
     git rev-parse --git-path info/exclude
     ```
  2. 取得した除外設定ファイルに、`.skillset/` および自身が管理するリンクのパスを追加します（末尾にスラッシュを付けない形式で記述します）。
     ```text
     .skillset/
     .agents/skills/client-a-artifacts
     .claude/skills/client-a-artifacts
     ```
     ※ `.agents/skills/client-a-artifacts/` のように末尾にスラッシュを付けた記述は避けてください。
  3. 特定のスキルリンクのみを除外し、他者が管理するスキルディレクトリ全体を誤って除外対象に含めないように注意します。なお、Git の作業ツリー環境では除外設定ファイルが複数の作業ツリー間で共有される場合があります。

- **sync および watch 実行時**:
  `sync` および `watch` による実際の同期が成功した場合、リポジトリローカルの除外設定ファイル（`git rev-parse --path-format=absolute --git-path info/exclude`）へ、ルートを基準とする `.skillset/` および管理対象シンボリックリンクの正確なパスが自動的に追加されます。
  - 追跡対象ファイル（tracked files）や `.gitignore` は一切変更しません。
  - 既存のバイト列を保持し、不足している行のみを末尾に追記します（重複行は追加しません）。
  - 変更前に `git ls-files` を実行し、リンク配置先またはその配下のファイルが既に Git で追跡されていないか検証します（追跡中のファイルは管理・置換できません）。
  - 除外設定ファイルがシンボリックリンクまたは通常ファイル以外である場合は処理を拒否します。
  - 改行コードを含む不正なパスの注入は拒否されます（スペースを含むパスは許容されます）。
  - 作業ツリー間で除外設定ファイルが共有されている場合を考慮し、隣接する永続的なロックファイル（`flock`）を用いて読み込みと追記を直列化します。
  - マッピングの解除時や衝突エラーの発生時には、除外設定の削除や変更は行いません。

### グローバル環境からの移行手順
プロジェクトごとの個別管理へ移行する際の標準的な手順です。
1. グローバル環境に配置されている既存のスキルを棚卸しし、バックアップを作成します。
2. 利用者がプロジェクト管理へ移行すべき対象スキルを分類・選定します。
3. 承認された範囲に限り、グローバル側のコピーやシンボリックリンクのみを除去します（スキルの原本は保護します）。
4. 対象のリポジトリで `skillset apply` または `skillset sync` を実行し、プロジェクトローカルなリンクを作成します。
5. 新規に起動した Codex や Claude のセッションにおいて、スキルが正しく認識されるか検証します。

- 注意点:
  - ツールによる同名スキルの警告検知は完全なものではありません。
  - 各エージェントの実機によるスキルの認識確認は、CLI の単体テストとは別個に実施する必要があります。

### ロールバックと非対応機能
- 移行前の状態に戻す（ロールバックする）場合は、リポジトリで `skillset remove` を実行した上で、バックアップからグローバル側の設定やリンクを復元します。
- 本ツールは、Git フックの登録、スキルの自動ダウンロード、MCP 設定ファイルの管理、およびグローバル環境からの自動移行機能は提供しません。
